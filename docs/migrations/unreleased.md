**This guide describes the four unmerged native groups in local `worktree/rapid-harbor-d2a6` at `bf23ced1649fd0074aec8736644c8f02aa0c492b`, plus separately labeled selectable menu-bar mode, custom icon image, and worktree removal additions in the current working copy; neither is in `main` or the stable public v0.1.11 binary.** The original four groups—contextual Settings/conditional rescue, independent character/bubble visibility, compact observation settings, and standalone/remote-only watcher startup—are implemented in that historical local checkout. The menu-bar choices and worktree removal are **not** attributed to that commit. Documentation and publishing tools are on `main`, but that does not merge these native features. The pinned stable public app and working-copy app version remain **v0.1.11**; the separate optional beta below uses an isolated snapshot. The branch/commit identify implementation, not a guaranteed fetchable public remote. Inline replies already shipped in v0.1.6; see the [composer migration](v0.1.4-to-v0.1.6.md).

For `main` or the public binary, use the [root installation and runtime guide](../../readme.md): the baseline uses its existing menu-bar settings entry point and Local/Remote observation controls. Do not expect this guide's independent visibility, conditional rescue, selectable menu-bar mode, custom icon image, worktree removal, compact observation UI, contextual Settings, or watcher startup correction from a `main` source build. The original four-group behavior below is scoped to the identified historical local checkout; the new menu-bar mode/image and worktree removal sections apply to the **current working copy only**. Shared configuration, data-preservation, IME, delivery, and host-capability warnings still matter.

The standard installer expects stable `v` version tags and the original app name: **do not use its default or `--prebuilt` path to install this beta**. ## Preserve the existing profile

Keep existing `HERDR_PLUGIN_CONFIG_DIR` / `HERDR_PLUGIN_STATE_DIR` or the same Herdr XDG plugin profile. Back up configuration before replacing the app. Retain `lifecycle.json`, `preferences.json`, and `characters/`; upgrading is not a reason to delete or recreate them. Saved character selection/imported revisions and personal dialogue remain in their existing stores; only saved dialogue survives restart, and reply/editor drafts are in-memory for the current run. Lifecycle switches remain owned only by `lifecycle.json`, including legacy `enabled` → `auto_start` migration retaining false and missing `exit_with_herdr` defaulting off for existing profiles (new profiles default on/on). Preserve endpoint/startup/unrelated fields and unknown preference keys; invalid settings report errors, and failed saves retain prior switches and live policy rather than resetting the profile. External `--assets` dialogue remains keyed by the activation-time canonical path; a renamed path on restart does not migrate that key.

For this working copy, include `menu-bar-icons/` from the same configuration directory in the backup alongside `preferences.json`, `lifecycle.json`, and `characters/`: `preferences.json` may contain `menu_bar_icon.asset` referencing a managed imported image. Backing up only the preference does not preserve its image.

**Only if you already possess the identified local implementation**, run `bash scripts/install.sh --source` from that checkout, using the [source installation guide](../../readme.md#install-this-checkout-from-source) for toolchain, packaging, and patched-host linking instructions. The command builds the current checkout; it does not retrieve the local branch or switch implementations, and on `main` it does **not** provide these native previews. Optionless installation normally fetches the pinned v0.1.11 binary; `--prebuilt` never falls back to source. Keep the existing native executable, action IDs, and character pack format. No app/host release, remote plugin auto-install, new configuration profile, or SSH transport change is required by this guide. Do not assume downgrade compatibility for data written by a newer checkout.

## Visibility is independent, not lifecycle

| Character | Bubble | Local pending-checkout result |
| --- | --- | --- |
| Visible | Visible | Attached bubble |
| Visible | Hidden | Character only |
| Hidden | Visible | Movable, tailless standalone bubble with session cards/replies |
| Hidden | Hidden | Neither window shown; app/session still running, rescue icon available |

`show` / `hide` / `toggle` affect only character visibility. Bubble visibility remains controlled separately by `show_bubble` / `hide_bubble` or **Bubble → Bubble visible**. Hiding the character does not hide an enabled bubble. Without a saved standalone origin, first detachment uses the **last actually applied attached bubble body**, not a speculative placement; the character origin is never substituted. A saved standalone origin takes precedence on later detachments, including during marked text. Showing the character reattaches the bubble; dragging the standalone background moves only the bubble. Compact/expanded changes and reply reflow preserve the origin unless screen clamping is needed; display removal/layout changes recover an offscreen bubble onto a remaining screen.

Card selection, compact/expanded/reply state, and drafts survive character hide/show during the run; drafts do not survive restart. Marked text defers standalone-origin saving until composition ends, including hide/show and placement/reset changes; the latest scene and later reset take precedence over older deferred geometry. Placement settings changed while standalone wait for reattachment. `reset` resets the character position and clears/reseeds the standalone origin from the newly applied attached layout where eligible, without changing either visibility preference or copying the character origin. With no saved or eligible attached origin, the normal attached layout supplies the fallback. **Close Bubble Window** still hides only the bubble, preserving the app/character/session and run-local drafts, and persists bubble visibility. In the actual isolated AppKit composer, `setMarkedText`/`unmarkText` callbacks retained marked text, the committed draft and selection across hide/placement/reset; the attached window/input frames stayed unchanged while marked, and the saved origin then committed after unmark. This is not physical IME, active-focus, drag, or display-topology proof.

Full-window passthrough applies to both windows, including standalone bubble and inline replies. Alpha passthrough applies only to character artwork, not the bubble; its pointer polling can race with click routing, so leave it off if that is unacceptable.

## Settings and historical conditional rescue

Right-click or Control-click the character, bubble background, or card header and choose **Settings…** to open the same full three-tab panel. Text fields retain native editing menus; buttons, dropdowns, and scrollbars retain native interactions. Canceling the bubble menu preserves selection/drafts. Bubble **Settings…** and **Close Bubble Window** are disabled while IME marked text is active and recheck that condition when chosen. Finish composition before reopening the menu. App activation is requested with the current macOS API and a macOS 13-compatible path; macOS decides whether keyboard focus transfers.

In the original `bf23ced` checkout, the rescue menu-bar icon appeared **only if both windows were hidden or full-window passthrough was on**, including after restart and while Settings was open. Both-visible, character-only, and interactive standalone-bubble-only states used no menu-bar slot. Alpha pointer polling alone did not toggle the icon. A standalone bubble offered **Show Character** in its own menu. The **current working-copy default is different**; see the selectable mode below.

**Show and Enable Character / 캐릭터 표시·조작 복구** shows the character and turns off full-window passthrough. It preserves bubble visibility and alpha passthrough: a visible bubble reattaches, a hidden bubble stays hidden. This is a partial preference change, not a full reset. The rescue menu also offers **Settings…** and **Quit**. CLI `show` is not the rescue action: it changes character visibility without enabling the bubble or clearing full-window passthrough.

## Current working-copy additions: menu-bar visibility and image

The existing three-tab native Settings panel includes **Menu bar icon / 메뉴 막대 아이콘** with **Always show / 항상 표시** (`always`) and **Only when recovery is needed / 복구가 필요할 때만 표시** (`recovery_only`). The default artwork is a template pawprint; custom images use the same status item and menu. Missing `menu_bar_mode` in `preferences.json` defaults to Always, whether the profile is new, legacy, or from the original conditional-rescue checkout. Keep the existing profile; selecting RecoveryOnly explicitly saves it across restart and unrelated preference saves. Unknown preference keys and other settings remain intact. There is no CLI mode command, extra status field, or new hotkey.

Always keeps the icon present while the app runs. RecoveryOnly shows it only if **both character and bubble are hidden or full-window passthrough is on**, including on restart and while Settings is open; an interactive standalone bubble or alpha passthrough alone does not trigger it. Both modes offer **Settings… / 설정…** and **Quit / 종료**. Only when recovery is needed does the menu offer **Show and Enable Character / 캐릭터 표시·조작 복구**, which shows the character and clears full-window passthrough without changing bubble visibility or alpha passthrough. In Always mode the icon remains after recovery; in RecoveryOnly it disappears after the menu closes when the trigger has cleared. CLI `show` still only changes character visibility.

Saving the mode does not alter window visibility, full-window or alpha passthrough, standalone/bubble geometry, drafts, or lifecycle. If saving fails, the prior selected mode and live icon remain unchanged. This addition does not recreate the profile or change the public version or binary. Actual composer callback/frame/draft/selection observations are described above; keyboard focus, physical IME, chooser, VoiceOver, and pointer interaction remain unverified because the app windows could not receive input.

**Choose image… / 이미지 선택…** imports a static PNG up to 4 MiB encoded and 1 million decoded pixels; animated, corrupt, truncated, and fully transparent images are rejected. The image preserves its colors, aspect-fits within 18 pt, and includes 1×/2× Retina representations rather than becoming a template. **Restore default icon / 기본 아이콘 복원** returns to the template pawprint. The optional `preferences.json` field `menu_bar_icon.asset` references the managed copy under the configuration directory's `menu-bar-icons/`; the external original can then move or be deleted. Missing `menu_bar_icon` uses the default pawprint. Import/save failure keeps the previous icon and settings. If a managed file is missing or corrupt on restart, the default is shown with an error while custom-image metadata remains for recovery. Restore changes only the image, not `menu_bar_mode`, character/bubble visibility, passthrough, geometry, drafts, or lifecycle. Back up the managed directory with the profile as noted above.

PNG import checks all chunk CRCs (including ancillary chunks and IEND), IDAT zlib Adler-32, and the exact inflated scanline bound for the color format and interlace passes before native decoding; the existing 4 MiB/1-million-pixel limits and supported formats remain unchanged. New managed images are published atomically without replacing an existing file. An older interrupted import may leave a saved image and a legacy private temporary hardlink; startup leaves it untouched and retains the custom-image metadata, showing the default with an error if the managed image cannot load. Keep the profile and explicitly reimport the **identical valid PNG** through **Choose image…** to repair only a confirmed owned/private same-inode temporary alias. This is not a startup cleanup or a repair for arbitrary hardlinks, other files, or corrupt PNGs.

An isolated check against the actual current binary seeded an **already-installed private managed PNG**, deleted only its external source, restarted the app, and observed the real status-button image still non-template at 18 pt with 18×18/36×36 bitmap representations. The saved icon choice and unknown preferences survived restart. This tests managed-asset startup restoration, **not** the chooser, new import, rejection, or visual/VoiceOver interactions; those remain unverified.
After opening actual Settings via the status-menu action, AppKit `performClick` on the enabled **Restore default icon** button ran its production reset callback. The status image became a template, only `menu_bar_icon` disappeared from `preferences.json` (all other known/unknown fields stayed identical), and the old owned managed PNG was unlinked. This is a guarded callback observation, not physical click, chooser Cancel/valid/corrupt PNG selection, or VoiceOver proof.

## Current working-copy addition: removing a linked worktree

No profile migration or new preference is required. This destructive command exists only in this current working copy, not the historical four groups, `main`, or the public v0.1.11 binary. Keep the existing profile and backups. A header right-click/Control-click targets that card even if another is selected; a bubble-background click targets the selection captured when the menu opens. The target is named explicitly. Without an eligible selected local linked worktree there is no removal item; native text/control menus are unaffected, and **Close Bubble Window** only hides the bubble. Remote cards and the main repository checkout are not removal targets.

Eligibility requires a current live local session, valid generation and unique coherent positive linked-worktree metadata. Absent, malformed, or ambiguous optional metadata on an older server leaves observation working and omits the deletion item. If metadata is available but `worktree.remove` is unsupported, an attempted operation reports that limit without a fallback; unsupported capability alone does not necessarily hide the menu item. The local observation minimum is **not** a deletion capability promise. The confirmation lists the repository, exact checkout, workspace, affected tabs/panes/processes and retained branch, and warns **IGNORED FILES WILL BE DELETED**. Ignored files can be removed even with `force: false`; back up anything needed, including ignored build outputs. **Cancel** is first and the default for Return, keypad Enter, and Escape; **Delete** is separate and second. After alert layout, the Cancel button cell is explicitly made the default or removal is aborted; a scoped Escape handler invokes the same Cancel action and is removed when the alert ends. No trash, undo, or branch deletion is provided.

The menu captures the target and revalidates it after confirmation with a fresh snapshot. IME marked text disables the action and is rechecked; only one operation can be pending. It sends one asynchronous `worktree.remove` with `{workspace_id, force: false}`. Dirty tracked/untracked/submodule and locked checkouts are refused by the backend rather than forced. There is no shell/git fallback, `force: true`, automatic trust, optimistic local purge, or automatic retry. After an attempted write with uncertain delivery, treat the result as **indeterminate** and inspect the checkout/workspace before any manual new attempt; never assume it failed or auto-resend. Feedback persists in the common bubble even after the row disappears, selection changes, or the window is hidden and reopened. Normal watcher refresh (about five seconds) remains authoritative.

The API accepts `workspace_id` only, not an expected checkout or generation: client-side fresh validation is **not an atomic compare-and-swap** against a restart or workspace rebinding. Worktree API support is separate from client-attach auto-start and its patched-host requirement below. The isolated live worktree exercise used stock Herdr 0.9.3; do not infer deletion support from the 0.9.0 local-observation baseline. Native tests/build and live backend/sender checks are recorded in the [Unreleased notes](../releases/unreleased.md#current-working-copy-addition-remove-linked-worktree). A top-layer Window Server shield blocked actual alert Return/keypad Enter/Escape, focused Delete, right-click, and physical IME input; configured Cancel behavior is not keyboard-action proof. It does not establish whether the screen was locked.

## Remote observation keeps saved choices and stays read-only

**This Mac** defaults on; **Remote machines** defaults off. Their right-aligned native switches are separate from saved profiles nested under **Machines to observe**. Rows distinguish machine name, saved session, and status. Content-sized rows/cards/scrolling replace fixed gaps and duplicate help; controls keyed by opaque profile ID retain focus/scroll during polling or renaming, and scrolling clamps if the list shrinks. Labels/contextual accessibility names are Korean/English.

The UI distinguishes initial catalog lookup, confirmed empty, no selection, paused, checking, observing, unavailable, and disabled. A failed catalog refresh retains the previous list with an explicit stale-list warning. Remote off preserves selections but masks stale successful statuses with observation-off feedback. Registering/renaming a machine does not implicitly select a new profile. Disabling/removing profiles excludes them without stopping remote processes. All sources off yields Unknown; source switches affect display counts/state/reactions, while the card filter only narrows displayed cards.

Set up SSH, add/authenticate machines, and approve any server setup manually in an [interactive Herdr terminal](https://herdr.dev/docs/0.9.2/connecting-machines/). Each selected enabled saved profile observes one saved remote session, not its whole host. The remote needs a compatible running server, not the pet app/plugin. Catalog refresh and selected-profile polling run about every five seconds (catalog refresh continues with Remote off); brief transitions can be missed. Retained disconnected cards are last-known offline/unknown data, not live status. After recovery/reselection, the first snapshot is a baseline, not a replay of old completion reactions.

Registration help and folded diagnostics are read-only. **Copy reconnect command** copies a shell-quoted `herdr machine reconnect '<profile-id>'` command with native clipboard feedback; it **never executes it**. Find IDs with `herdr machine list`, then run recovery yourself in a terminal. The pet does not prompt for credentials, install remote software, change SSH transport, or fall back to Local on remote failure. Remote cards remain observation-only; prompts never use machine forwarding.

## Remote-only startup and watcher shutdown

Run the pet on the **local Mac**. Authenticate the saved machine in a terminal, enable **Remote machines**, then explicitly select its enabled profile. Attaching to a remote session or registering a machine alone does not enable its observation. If there is no healthy local server yet, optionally use the native CLI **before the first start**:

```sh
herdr-desktop-pet settings set exit_with_herdr off
```

A source install can use `./dist/HerdrDesktopPet.app/Contents/MacOS/herdr-desktop-pet` instead of the installed CLI. The native settings command works with the pet stopped, no host, or a disabled plugin and does not launch a pet; a Herdr plugin action still requires a live enabled host. Once remote polling is healthy, optionally set `exit_with_herdr on` again.

**This Mac off excludes local display data, not local endpoint lifecycle.** A valid local `plugin_list` with no desktop-pet entry on first observation is not disable: keep local snapshots/subscription and remote polling available. Explicit `enabled: false` detaches that endpoint. A missing entry after this daemon previously observed either an enabled or disabled row is observed unlink and detaches too. Membership history survives rechecks/reconnects within this daemon, not a new daemon.

If **every registered local endpoint is confirmed disabled/unlinked**, the pet quits immediately, even with healthy remote polling or `exit_with_herdr` off. Initial missing is not that terminal condition. Other loss-of-health cases use the existing 30-second grace when exit is on, including initial no-server start; healthy reconnection cancels it and one healthy server prevents exit. Client detach is not server loss; stale endpoints/failed retries never extend grace. Switching exit off cancels a countdown, and enabling it while disconnected starts a fresh 30 seconds. Stop/Quit end only this run; auto-start can relaunch on a later qualifying event unless turned off. Changing auto-start never forces the current pet to stop or show.

## Diagnose capabilities separately

Local observation supports Herdr 0.9.0+. Remote polling needs a local CLI with [saved-machine API forwarding](https://herdr.dev/docs/0.9.2/cli-reference/#saved-ssh-machines) (`herdr --machine <profile-id> api snapshot`, documented in 0.9.2) and a compatible remote server. Local replies separately need `agent.prompt`; the original evidence verified it with 0.9.2, not every server meeting the observation baseline. Offline/stale/unready/unsupported targets cannot send; no shell/SSH/raw-pane fallback or automatic retry exists. Check unknown delivery before resending, and handle approvals/questions in the real terminal. The API has no atomic expected-session guard, so last-instant pane occupant replacement remains a limit.

Client-attach auto-start separately requires official Herdr 0.9.3 source with the [client-attached patch](../../integrations/herdr/client-attached.patch) applied and built, or an actual host release advertising that hook. Stock 0.9.0/0.9.3 do not implement it; a manifest minimum version is not capability proof. Follow the [patched-host guide](../../integrations/herdr/README.md), use its `PATCHED_HERDR` rather than stable `herdr` on PATH, inspect link warnings, and verify subscription. Linking/enabling an already-running host alone does not launch the pet: start once or await a later qualifying attach.

For `Herdr watchers are shutting down`, identify the inherited `HERDR_SOCKET_PATH` / `HERDR_CLIENT_SOCKET_PATH`, the CLI executable/version on PATH, and the server owning that socket separately. A plugin list from another server cannot diagnose the daemon's observed endpoint. Check the intended CLI/socket/session together and the selected remote profile/forwarding version; a patched host does not install desktop-pet on any server.
