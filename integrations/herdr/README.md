# Herdr Desktop Pet host integration

**Requires a patched Herdr host.** Stock Herdr 0.9.0 and 0.9.3 do not provide the `client.attached` plugin hook. The pet manifest's `min_herdr_version = "0.9.3"` is only the baseline for the supplied patch; it does **not** prove hook support. Use this patch on the official Herdr v0.9.3 source at commit `7b116c05bfda646af39d2524c54e70c751f57ee8`, or a future *actual* host release that explicitly advertises `client.attached`. Do not rely on an unknown-hook manifest warning being fatal: Herdr can link the plugin while its attach hook does nothing.

Pet **v0.1.4 includes the lifecycle settings**; the older 0.1.3 prebuilt does not. The manifest's `[[build]]` runs `bash scripts/install.sh` without `--source`, so managed installs (`herdr plugin install hanbong5938/herdr-desktop-pet`) download the prebuilt release pinned to the manifest version anonymously with `curl`, verify it, install it into the plugin directory's `dist/`, and fall back to a source build only if the prebuilt is unavailable or invalid. `herdr plugin link` does not run `[[build]]`; for a linked dev checkout, run `bash scripts/install.sh --source` yourself to build local changes, as shown below. `scripts/install.sh --prebuilt` installs only the pinned prebuilt, with no source fallback. All installation modes still require the patched Herdr host for client-attach auto-start. Do not substitute an unpatched Homebrew/stable Herdr binary for the patched binary.

## Build in separate checkouts

Prerequisites: macOS arm64 for the pet; Rust/Cargo, Bun, npm, Xcode command-line build tools and the tools needed by the two source trees. Build the Herdr host with the repository's normal locked Rust toolchain and native dependencies (including Zig 0.16.0 for vendored libghostty-vt); consult the official Herdr `README.md` and `AGENTS.md`. `just` is needed for its test/check recipes. For the full `just check` on macOS, the Herdr Windows cross target additionally needs `cargo install xwin --locked` and `just setup-windows-cross` (interactive SDK license acceptance; see Herdr `CONTRIBUTING.md`). Ordinary macOS builds do not need the Windows SDK.

From the **pet source** checkout, keeping its absolute path for linking:

```bash
PET_ROOT="$PWD"
HERDR_SOURCE="$(mktemp -d "${TMPDIR:-/tmp}/herdr-v0.9.3-patched.XXXXXX")"
git clone https://github.com/herdrdev/herdr.git "$HERDR_SOURCE"
cd "$HERDR_SOURCE"
git checkout 7b116c05bfda646af39d2524c54e70c751f57ee8
git rev-parse HEAD  # must be 7b116c05bfda646af39d2524c54e70c751f57ee8
git apply --check "$PET_ROOT/integrations/herdr/client-attached.patch"
git apply "$PET_ROOT/integrations/herdr/client-attached.patch"
# Optional built-in Pet Plugin Manager host support (in addition to the Pet hook):
git apply --check "$PET_ROOT/integrations/herdr/plugin-manager.patch"
git apply "$PET_ROOT/integrations/herdr/plugin-manager.patch"
just test
just check       # after setting up the Windows cross target as described above
cargo build --release --locked
```

Use `"$HERDR_SOURCE/target/release/herdr"` explicitly as `PATCHED_HERDR` below. Do **not** copy it over an installed Herdr, replace an existing server, or change your update channel implicitly. Start and inspect a separate disposable Herdr session with the patched binary (and avoid inherited `HERDR_SOCKET_PATH` / `HERDR_CLIENT_SOCKET_PATH` from another session; see the host's `AGENTS.md`). API/schema checks must use the *same patched binary* and target session, not a stable binary already on `PATH`.

The second patch is required for Pet's **built-in optional Plugin Manager**; there is no independent Manager app or helper to install. Apply `client-attached.patch` first, then `plugin-manager.patch`, before building the isolated host. Stock v0.9.3 does not support these commands. Pet settings initially show the Manager as not installed; **Install** only enables availability, **Remove** only disables availability, and **Open** explicitly starts discovery on the selected socket. Neither availability action changes a plugin. Discovery authenticates the same-UID server PID and canonical executable and binds the selected socket, host and canonical config/state profile; stock and older protocol-2 hosts, including ones without manager inventory, may supply ordinary read-only inventory where available. All five mutations require capabilities identifying `product_id: "herdr-plugin-manager-host"` with `durable_result_protocol: 1` and `admission_fd_protocol: 1`, plus `protocol: 2` and `manager_safety_protocol: 1` in both capabilities and live context. There is no older-protocol or alternate-host/CLI mutation fallback.

The regenerated Manager patch ships all 18 affected files, including `plugin_paths.rs` and the generated `docs/next/api/herdr-api.schema.json` with the required existing Manager methods. Consumers apply the patches in the order above and build; **no manual schema regeneration is required**. Fresh pristine apply/check on the pinned commit, byte equality for all 18 source files, production build, strict Clippy and 3,735 host nextest tests (12 skipped, superseding the earlier 3,733) were exercised with Rust 1.96.1, plus 155 auxiliary Python and 67 bundled Bun tests. This does not replace an installed host or establish a published release. The existing protocol 2, safety/durable-result/admission fields and named client endpoint generation 1 are unchanged; no new wire version, capability, public Pet/Manager command, app, crate or dependency was added.

The host supplies `herdr plugin manager capabilities --json`, `context --socket ABS --json` (selected socket, canonical host executable and server config/state/PID), and internal `apply --request ABS_JSON --admission-fd N`. Do not invoke `apply` by hand: Pet acquires the owned private per-operation `operation.lock` before submitting a synced request, hands the locked descriptor to the CLI, and observes the CLI's bounded, fsynced, atomically published `result.json` only after the lease ends. Compact newline-free file JSON has inclusive entire-file limits of 1 MiB for requests and 128 KiB for results; parent directories are synced before active publication or spawn, including repeated submissions. The CLI adopts the exact lock inode and sets close-on-exec immediately so build/git descendants cannot prolong the lease. Output, parent lifetime and a missing result never prove success: ended unknown operations retain their original ID for explicit review and acknowledgement, never replay. Request, lock, staging and result are checked relative to a private operation directory before mutation; short shared-profile admission is released before host RPC or long-lived operation work.

Enable/disable apply to all valid nonprotected registered plugins (including managed or no-source entries) according to current enabled state. Successful Disable clears only the matching agent view, not pane ownership, terminals, files, config or state. Unlink applies only to local links and retains their files; update/uninstall require a complete managed GitHub checkout, retain config/state and preserve disabled state and recorded ref on update. Successful Unlink/Uninstall also release that plugin's pane ownership records, without closing the underlying terminals. The manager obtains fresh display metadata and raw registration from one read-only inventory snapshot; both are checked at confirmation and mutation. Update verifies the preserved old checkout manifest and remaps only its verified root/manifest metadata, rather than trusting a new manifest at the original path. The actual RPC stream authenticates peer UID, original PID and executable; the server checks original PID and immutable canonical config/state roots before lease validation or filesystem changes, rejecting a root redirected after confirmation. Ordinary managed CLI install/uninstall and Manager filesystem operations share `.plugin-install.lock`; ordinary server link/unlink/enable/disable requests take nonblocking `.manager.lock` admission and return `plugin_manager_busy` during a Manager transaction. Manager-only server mutations require the live CLI's private lease token. `desktop-pet`, its actual running executable/bundle, registered Pet roots, managed Pet checkouts, physical registry/lock/temp aliases and ancestor/descendant overlaps are protected for **all five actions**; ordinary stow outside Pet remains available. Pet holds a private config-scoped preferences-owner FD for its whole lifetime; offline settings must hold the same owner through save, even when selecting another state directory. Live helpers verify both canonical config and state before reading and writing. A released owner can rebind to another state profile; inaccessible or mismatched ownership fails closed. Accepted relative daemon config paths are made absolute before publishing the live profile; the existing absolute-state requirement is unchanged. None of this initializes the unused Manager store. Availability Remove refuses an operation still running in any process. Hiding the Manager or quitting Pet does not cancel a submitted CLI operation or change the normal Pet shutdown/update behavior.

Relative config input is resolved against the actual process CWD for offline Pet availability changes and every host path, then represented as a standard absolute path with its physical identity. State, arbitrary protected paths, stored managed paths and request paths remain absolute-only. Logical config aliases and physical roots stay distinct through context, registry/install/manager locks, lease verification and expected checkout/temporary paths. `ProfileOperationStore` resolves config before its unchanged leaf-symlink, private-owner and inode checks. The registry boundary is the immutable `original_context.config_dir`, pinned before creation/locking and checked again during precommit, not a mutable current context or stow destination. A separate outside-config stow target remains supported. Ordinary trusted install produces canonical managed metadata; the Windows runtime-root expected representation matches its existing helper, but Windows compile/runtime was not exercised. Ambiguous old relative `managed_path` is rejected, not rebased or migrated.

Availability helpers use typed probes initially, again while holding the state lease, and while waiting for owner release. Only connect-time `NotFound` or `ConnectionRefused` proves absence; a connected timeout or empty EOF never does. Permanent framing/parse, `InvalidData`, `InvalidInput` and permission errors remain failures even after socket disappearance. The authentic atomic-stopping `ping` error (`desktop pet is stopping`) counts as a live owner under the normal owner/profile checks. One bounded startup-readiness/stopping-owner deadline applies only before submission, through the counted mutation write; existing post-submission recovery windows are separate. Offline saving requires exclusive ownership before Set entry. Every result after Set entry is returned directly, even a zero-byte send failure, with no offline fallback or replay; partial transmission retains exact-ID uncertainty. A matching startup helper waits, a wrong-state live owner fails without overwrite, and a stopping owner must release ownership before offline saving. Install/Remove write only availability and necessary admission metadata; unused Manager operation stores/jobs are not created.

The installer and backup checks share one exact-layout predicate: canonical checkout plus a grammar-validated, lexically joined recorded subdirectory, not a canonicalized redirected root. The component grammar accepts nested paths, `@scope`, spaces and Unicode within existing constraints; traversal, NUL, backslash, colon and symlinks remain rejected. The expected runtime root and exact canonical manifest must match, with Windows retaining its existing runtime-root representation. Fresh checks guard pre-build, post-build, pre-network/swap and final post-swap boundaries, server admission and fresh in-lock validation, plus the preserved old backup. Update verifies old backup root/manifest identity and old-registration CAS rather than trusting new metadata at the old path. Definitive local post-swap failure restores the old checkout through existing rollback, or returns Partial with the old backup retained when inventory is inconsistent; Unknown behavior remains unchanged. Registry durability barriers traverse both existing and newly created ancestor chains on each operation, without a global durable cache. The temporary file is full-synced, `renameat` replaces the registry, then the **same pinned target-parent FD** is full-synced before completion. Typed `PreCommit` errors are definite failure with unchanged registry; post-rename `CommitUnknown` becomes the existing `plugin_manager_registry_uncertain` API error and the existing mutation-only unknown status. App memory, pane ownership and agent views change only after durable success. Unknown Update retains new checkout plus old backup; unknown Uninstall retains checkout plus user data. All five actions remain blocked through canceled review until explicit exact-ID acknowledgement, which never replays the mutation.

Back in the pet checkout, build its packaged app explicitly from local source, then link the source directory with the patched host. Herdr `plugin link` does not execute the manifest build command:

```bash
cd "$PET_ROOT"
./scripts/install.sh --source
PATCHED_HERDR="$HERDR_SOURCE/target/release/herdr"
HOST_PROFILE="$(mktemp -d /tmp/herdr-pet.XXXXXX)"
export XDG_CONFIG_HOME="$HOST_PROFILE/config" XDG_STATE_HOME="$HOST_PROFILE/state"
export XDG_DATA_HOME="$HOST_PROFILE/data" XDG_CACHE_HOME="$HOST_PROFILE/cache"
unset HERDR_ENV HERDR_SOCKET_PATH HERDR_CLIENT_SOCKET_PATH HERDR_CONFIG_PATH
unset HERDR_PLUGIN_CONFIG_DIR HERDR_PLUGIN_STATE_DIR
"$PATCHED_HERDR" server &
# Wait for this server's "api socket:" message before the commands below.
"$PATCHED_HERDR" plugin link "$PET_ROOT"
"$PATCHED_HERDR" plugin list
"$PATCHED_HERDR" api schema --json
```

Inspect the `plugin list`/`plugin.link` warnings for `unknown event 'client.attached'`; no such warning should appear. Inspect the printed API schema for a `client.attached` subscription and `client_attached` event. An explicit raw API probe on the patched session is `{"id":"attach_probe","method":"events.subscribe","params":{"subscriptions":[{"type":"client.attached"}]}}` sent to its API socket: require a successful subscription acknowledgment, attach a **shell or terminal** client to the same session, and observe an event with `event: "client_attached"`, `data.type: "client_attached"`, server-local numeric `data.client_id`, and `data.client_kind: "shell"` or `"terminal"`. A plain API request, failed client handshake, or handoff must not emit attach. A successful link or version match alone is **not** this capability check.

## Lifecycle behavior

The manifest keeps the server-ready `[[startup]]` ensure and adds a distinct `client.attached` ensure for each successful client registration. These are asynchronous plugin hooks, filtered by the host plugin enabled state and macOS platform; ensure is idempotent and does not force an already running/hidden pet visible. Host `plugin disable` or `unlink` remains separate from pet lifecycle preferences. Client detach is **not** server death. Outside the confirmed-disable/unlink shutdown below, `exit_with_herdr` ON quits after the last healthy server has been absent for 30 seconds (including initial absence); turning it OFF retains independent operation. Fresh settings default both `auto_start` and `exit_with_herdr` ON; upgraded profiles preserve the old independent exit behavior (OFF), and legacy `enabled=false` maps to `auto_start=OFF`. Manual start is independent of auto-start, and stop/Quit does not change the preference.

On a newly observed local endpoint, a successful `plugin_list` without `desktop-pet` is valid standalone observation, **not** a disable: the pet may still take local snapshots and observe selected remote profiles. An explicit disabled desktop-pet entry detaches that endpoint. Once this daemon has observed an enabled or disabled desktop-pet entry there, a later missing entry also detaches it as an observed unlink; rechecks/reconnects do not erase this memory, but a new daemon starts without it. If every registered local endpoint is confirmed disabled/unlinked, shutdown is immediate regardless of a healthy remote profile or `exit_with_herdr = off`. An initially missing entry is not terminal, and other server-loss cases keep the normal healthy-connection grace.

For remote-only use, run the pet on the local Mac. Add/authenticate a saved SSH machine with the local Herdr CLI in a terminal, then enable **Remote** and select its enabled profile in the pet's **Observation sources**; attaching remotely or saving a machine alone does not select it. The remote host needs a compatible Herdr server, **not** the pet app/plugin. Turning **Local** observation off excludes local display data, not the registered endpoint from lifecycle monitoring. With no healthy local server, optionally set `exit_with_herdr` off via the native CLI **before starting the pet for the first time**, then turn it on after healthy remote polling if desired. This does not install any plugin or alter SSH transport. Diagnose the socket the pet/CLI actually inherits (`HERDR_SOCKET_PATH` / `HERDR_CLIENT_SOCKET_PATH`) separately from the Herdr executable/version on `PATH`: `plugin list` on a different socket does not describe the observed endpoint. Keep the patched host requirement for `client.attached` auto-start; Homebrew installs the app/CLI only, not a plugin or patched host.

The Herdr `settings` plugin action launches the native settings window without starting the pet daemon, but Herdr actions require an available enabled host. For offline or host-disabled use, call the **packaged native binary directly**; these commands do not require Herdr and settings get/set do not launch the pet:

```bash
PET="$PET_ROOT/dist/HerdrDesktopPet.app/Contents/MacOS/herdr-desktop-pet"
"$PET" settings
"$PET" settings get
"$PET" settings set auto_start off
"$PET" settings set exit_with_herdr on
```

Pet v0.1.4 supplies the pet-side lifecycle changes, not the missing host hook. Client-attach auto-start still requires the supplied patch on official Herdr v0.9.3. Only advertise support for an unpatched host once a real host release explicitly ships `client.attached`; stock v0.9.3 does not.
